# 边缘计算优化建议

本文记录当前项目在边缘设备上运行时，性价比较高、工程上可落地的优化方案。

当前模型文件：

```text
models/pose_landmarker_lite.task
大小约 5.5 MiB
```

该模型已经是 MediaPipe Pose Landmarker 的轻量版本。当前阶段的主要瓶颈通常不是模型文件大小，而是视频输入、图像预处理、Python 调度、OpenCV 显示、日志 I/O 和设备散热。

## 推荐目标

第一阶段边缘部署建议先按以下目标调优：

```text
单路摄像头
单人检测
640x480 或 640x360
10 FPS 姿态推理
仅记录事件日志
无窗口后台运行
连续运行 30 分钟以上
```

姿态提醒本身有持续时间判断，通常不需要 25-30 FPS 的模型推理。稳定 10 FPS 比高帧率但延迟堆积更有价值。

## 当前可直接使用的优化

### 1. 降低输入分辨率

固定书桌场景不一定需要 720p。优先使用：

```yaml
video_source:
  width: 640
  height: 480
  target_fps: 10
```

如果摄像头视野足够，也可以尝试 `640x360`。降低分辨率通常是收益最高、成本最低的优化。

### 2. 关闭窗口显示

边缘设备正式运行时不建议持续显示 OpenCV 窗口：

```powershell
.\.venv\Scripts\python.exe main.py --source-type usb --camera-id 0 --no-window
```

显示骨架、文字、窗口刷新都会占用 CPU。调试时再打开窗口。

### 3. 只写事件日志

逐帧 CSV 日志会产生持续 I/O。边缘运行时建议：

```yaml
logging:
  enable: true
  write_each_frame: false
  enable_event_log: true
```

这样普通帧不落盘，只在低头、伏案、联合风险、严重风险真正触发时写入 `posture_events_*.csv`。

### 4. 保持 MediaPipe 视频模式

当前代码使用 MediaPipe Pose Landmarker 的 `VIDEO` 模式，并关闭了分割输出：

```python
running_mode=RunningMode.VIDEO
output_segmentation_masks=False
```

这是正确方向。视频模式会利用跟踪逻辑，避免每帧都做完整检测；分割 mask 对当前姿态提醒没有必要。

### 5. 启动时校准正常坐姿

桌面摄像头通常拍不到髋部，建议使用上半身代理分数时先校准：

```powershell
.\.venv\Scripts\python.exe main.py --source-type usb --camera-id 0 --calibrate-on-start
```

或者在窗口中按 `c` 重新校准。校准期间保持正常坐姿约 8 秒。校准可以降低相机高度、角度、学生体型差异带来的固定阈值误差。

## 下一步低成本代码优化

以下方案需要少量代码改造，但比模型剪枝更划算。

### 1. 降低推理频率

摄像头可以 25-30 FPS 取帧，但模型只需要 10 FPS 推理：

```text
取帧 FPS: 30
推理 FPS: 10
显示/提醒: 使用最近一次推理结果
```

姿态异常需要持续 2-3 秒才触发，10 FPS 已经足够。该优化能显著降低 CPU 占用。

建议新增配置：

```yaml
pose:
  inference_fps: 10
```

### 2. 只保留最新帧

边缘设备上不要让帧队列堆积。摄像头读取线程只保留最新帧，推理线程忙时丢弃旧帧：

```text
camera thread -> latest_frame
inference thread -> copy latest_frame
```

这样即使某一帧推理慢，也不会导致提醒延迟越来越大。

### 3. 固定 ROI 裁剪

书桌场景机位固定，可以只处理学生所在区域：

```yaml
video_source:
  roi:
    enable: true
    x: 160
    y: 60
    width: 760
    height: 620
```

ROI 可以减少背景干扰和处理开销。需要注意：裁剪后关键点坐标要映射回显示画面，或者在裁剪画面上独立显示。

### 4. 降低显示频率

如果需要窗口调试，可以不用每帧都刷新 UI：

```text
推理 10 FPS
显示 10 FPS
日志按事件写
```

调试界面应服务于校准和观察，不应成为边缘部署的性能瓶颈。

### 5. 增加性能指标日志

建议补充以下运行指标：

```text
capture_fps
inference_fps
inference_latency_ms
frame_drop_count
cpu_temperature
```

树莓派 5、RK3588 这类设备持续运行时，散热和降频会直接影响稳定性。

## 暂不推荐的优化

### 1. 直接剪枝当前 .task 模型

不建议当前阶段做模型剪枝。原因：

```text
MediaPipe .task 不是普通 PyTorch/ONNX 模型
内部可能包含检测模型、关键点模型和图配置
剪枝后需要重训、量化、验证精度、重新封装或更换推理框架
当前项目的主要问题不是模型太大，而是机位、校准、帧率和工程流水线
```

剪枝适合后期有训练数据、明确目标硬件、并且准备更换模型部署链路时再做。

### 2. 为 NPU 强行改造当前 MediaPipe 模型

RK3588、Jetson 等设备的 NPU/GPU 很强，但当前 `.task` 模型不能直接等价迁移到 RKNN 或 TensorRT。若要使用硬件加速，建议后续单独评估：

```text
MoveNet Lightning TFLite
RTMPose-tiny -> ONNX -> RKNN
RTMPose/YOLO-Pose -> ONNX -> TensorRT
```

## 硬件建议

### 首选低风险方案

```text
Intel N100 小主机
8GB 或 16GB 内存
USB 摄像头或 RTSP 摄像头
```

优点是迁移成本最低，当前 Python + OpenCV + MediaPipe 项目基本可以直接跑。

### 低功耗 Linux 方案

```text
Raspberry Pi 5 8GB
主动散热
官方 5V 5A 电源
640x480 / 10 FPS 起步
```

树莓派 5 可以作为边缘设备，但需要关注 ARM 上的依赖安装、摄像头兼容性和散热。

### 后续 NPU 方案

```text
RK3588 / Orange Pi 5 Plus
```

适合后续产品化降成本，但需要重新设计模型部署链路，例如 ONNX 转 RKNN。

## 推荐实施顺序

建议按以下顺序推进：

```text
1. 降分辨率到 640x480
2. 关闭窗口显示
3. 只写事件日志
4. 启动时完成正常坐姿校准
5. 增加 10 FPS 推理限频
6. 增加最新帧队列，避免延迟堆积
7. 增加固定 ROI 裁剪
8. 再评估是否需要换模型或上硬件加速
```

这条路线比直接做剪枝更稳，也更容易用实际日志验证收益。
